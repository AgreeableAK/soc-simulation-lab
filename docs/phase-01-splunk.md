# Phase 1: Splunk SIEM

## 1. Overview

Phase 1 establishes **Splunk Enterprise as the central Security Information and Event Management (SIEM) platform** for the Modular SOC Simulation Lab.

The objective of this phase is to build the core monitoring and search capability that later phases will use for Windows endpoint telemetry, log collection, detection engineering, attack simulation, and SOC investigations.

The project architecture defines Splunk as the central security monitoring platform responsible for:

* Log indexing
* Event searching
* SPL-based analysis
* Security-focused data organization
* Dashboard development
* Alerting
* User and role management




## 2. Phase Objective

The objective of Phase 1 was to deploy and validate a functional Splunk SIEM instance capable of receiving, indexing, and searching security-relevant telemetry.

The target capability was:

```text
                 Splunk Enterprise
                        │
          ┌─────────────┼─────────────┐
          │             │             │
       Indexes       Searches      Dashboards
          │             │             │
          └─────────────┼─────────────┘
                        │
                 Security Monitoring
```

## 4. Splunk Installation and Initial Configuration

Splunk Enterprise was installed on `SOC-SPLUNK-01` and made available as the central SIEM platform.

Initial validation confirmed that the Splunk service and web interface were operational.

The Splunk environment was then configured for security monitoring rather than being used only as a default installation.

The Phase 1 configuration focused on:

1. Splunk availability
2. Index creation
3. Search functionality
4. SPL fundamentals
5. Event and field analysis
6. Security-focused data organization
7. Validation of indexed data


## 5. Security Index

A dedicated security index was created:

```text
Index:
soc_security
```

This index provides a logical location for security telemetry generated by the lab.

The index was verified from the Splunk command line.

Example validation:

```bash
sudo -u splunk /opt/splunk/bin/splunk list index | grep -i soc_security
```

The resulting configuration showed:

```text
soc_security
    /opt/splunk/var/lib/splunk/soc_security/db
    /opt/splunk/var/lib/splunk/soc_security/colddb
    /opt/splunk/var/lib/splunk/soc_security/thaweddb
```

This confirmed that the `soc_security` index existed and had the expected Splunk storage structure.

## 6. Index Validation in Splunk

The index was also validated through the Splunk Search interface.

A basic event count search was performed:

```spl
| eventcount summarize=false index=soc_security
```

The search returned the `soc_security` index and identified the Splunk server:

```text
index       provider    server
soc_security    local    soc-splunk-01
```

At this point, the index existed and was searchable, even though it initially contained no endpoint events.

This distinction is important:

```text
Index exists
      ↓
Search works
      ↓
Index can receive telemetry
      ↓
Endpoint telemetry is added in later phases
```

## 7. SPL Fundamentals

Introduced to the use of **Search Processing Language (SPL)** for querying and analyzing Splunk data.

Basic searches were used to understand:

* Event counts
* Index contents
* Log levels
* Hosts
* Sources
* Sourcetypes
* Event fields
* Time ranges

Examples included:

### Count events by log level

```spl
index="_internal" earliest=-30m latest=now
| stats count by log_level
| sort - count
```

This was used to validate Splunk's search and statistical processing capabilities.


## 7.1 Event Count

A basic event count was also performed:

```spl
index=soc_security
| stats count
```

This provides a simple method for determining how many events are currently available in the security index.

## 7.2 Count by Sourcetype

The following search was used to analyze event distribution:

```spl
index=soc_security earliest=-15m
| stats count by sourcetype
| sort - count
```

Once Windows telemetry was connected in the subsequent telemetry/log-collection work, the query showed sources including:

```text
XmlWinEventLog:Security
XmlWinEventLog:Application
XmlWinEventLog:System
```

This later validation demonstrated that the Phase 1 SIEM foundation could successfully process endpoint telemetry delivered by the following phases.

## 8. Event Field Analysis

Splunk was also used to inspect individual event fields.

A representative search was:

```spl
index=soc_security earliest=-15m
| table _time host sourcetype source EventCode EventID Message
| sort - _time
```

This exposed important fields including:

```text
_time
host
sourcetype
source
EventCode
EventID
Message
```

These fields are important for later SOC investigations because they allow an analyst to move from a high-level event count to individual event analysis.


## 9. Splunk Internal Data

Splunk's internal index was also queried during testing.

Example:

```spl
index="_internal" earliest=-30m latest=now
| stats count by log_level
| sort - count
```

The query returned Splunk internal log levels including:

```text
INFO
WARN
ERROR
```

This validated that SPL searches, aggregation, sorting, and time-based searching were functioning correctly.

This was useful as an initial Splunk validation before endpoint telemetry was connected.

## 11. What Was Learned

Phase 1 established several practical SIEM concepts:

### SIEM deployment

Understanding how the SIEM functions as the central monitoring platform.

### Indexing

Understanding that Splunk organizes incoming data into indexes and that security telemetry can be separated into a dedicated index such as:

```text
soc_security
```

### SPL

Developing familiarity with:

```text
search
stats
count
sort
table
earliest
latest
```

### Event fields

Understanding that SOC investigation depends on extracting and analyzing fields such as:

```text
_time
host
source
sourcetype
EventCode
EventID
Message
```

### Time-based investigation

Understanding that event analysis must be performed within an appropriate time window.

### Validation

Learning to validate Splunk both through:

```text
CLI
```

and:

```text
Splunk Web
```

rather than relying on the user interface alone.
